# M1 test results

Recorded 2026-10-08 on the author's machine (Intel Core i7-13700H, 13.7 GB RAM, Windows 11,
Temurin JDK 21.0.12.1, Maven 3.9.11, JUnit 6.1.3). Every JVM ran with `-Xmx1g` (Maven via
`.mvn/jvm.config`, the surefire fork via `argLine`, the CLI via the Makefile). CI re-runs the same
steps on Ubuntu with Temurin 21 on every push; CI results are not recorded here.

The work follows DMAIC: the problem and the critical-to-quality (CTQ) targets are defined in
[RFC 0001](../rfc/0001-design.md#critical-to-quality-measures-define); this file covers Measure,
Analyze, Improve and Control.

## Measure

### Baseline: what exact counting needs

The demo log has 1,000,000 lines and 88,222 distinct client addresses. Holding them exactly needs
at least 352,888 bytes even as packed 32-bit integers, and a Java `HashMap<String, long[]>` needs
several times that (object headers, strings, table). The sketches use a fixed 16,384 bytes
(HyperLogLog, p = 14) and 108,760 bytes (Count-Min, 5 x 2,719 longs), whatever the number of
clients.

## Analyze

- **HyperLogLog meets its CTQ.** The worst RMSE in 24 settings is 1.059 x `1.04/sqrt(m)`
  (p = 10, n = 100,000; target at most 1.25x). For p = 12 and 14 the RMSE stays at or below theory
  up to n = 100,000 and within 2.3% above it at n = 1,000,000. The p = 10 rows sit slightly above
  theory, as expected: `1.04/sqrt(m)` is an asymptotic value and the RMSE of 200 trials itself
  varies by about 5%. Bias stays within +-0.8%.
- **The classic estimator has a defect at its switch point.** Its RMSE rises to 2.870% at
  p = 12, n = 10,000 and 1.110% at p = 14, n = 50,000 (both near `2.5m`), 1.766x theory. Root
  cause: below `2.5m` it uses linear counting, whose error grows as registers fill; above, the raw
  estimate, which is biased upward at small ranges. Neither is accurate at the boundary.
- **Count-Min never under-counted** (0 of 5,722,728 estimates) and the fraction of items above
  `epsilon * N` was at most 0.0028%, about 240 times below `delta`. The bound is loose for skewed
  streams because the heavy items whose mass causes collisions are few.
- **Top-20 recall falls with a wide epsilon** (85.5% at `epsilon = 0.01`, skew 0.8): the over-count
  bound (9,994) is larger than the gap between the 20th and 21st items, so the heap cannot tell them
  apart. At `epsilon = 0.001` recall is 99.0 to 100%. The top-k guarantee is for items above
  `phi * N` (`HeavyHittersTest`), not for an exact top-k of near-equal items.
- **Defects found while building, and their root causes:**
  - The first bias assertion compared the mean error with `3 * RMSE / sqrt(trials)`. In sparse
    mode the RMSE is about 1e-5, so a tolerance built from it vanished and a near-exact estimate
    failed. Root cause: a relative tolerance with no floor. Fix: add `0.1 x 1.04/sqrt(m)` as a
    floor (documented in the test).
  - Spotless on Windows wrote CRLF line endings, so text matching in the mutation script missed one
    line. Root cause: the platform default. Fix: `<lineEndings>UNIX</lineEndings>` in the POM, so
    every platform formats identically.
  - With 5 trials per row, the bench's HyperLogLog ratio reached 1.361 and the gate failed; the
    RMSE of 5 samples is too noisy for a 1.25x limit. The gate is meant for the default 200 trials,
    which CI uses.

## Control

- **Unit tests hold every CTQ:** `HyperLogLogAccuracyTest` (RMSE, bias, estimator and sparse-mode
  improvements), `HyperLogLogTest` (memory never above `m` bytes, exact conversion),
  `CountMinSketchTest` (never under-counts, fraction over the bound below delta),
  `HeavyHittersTest` (no item above `phi * N` missed). All seeds are fixed, so a failure is a real
  change, not noise.
- **CI gates** (`.github/workflows/ci.yml`): Spotless check and `-Xlint:all -Werror` fail the
  build; the demo step fails unless its RESULT line reads
  `within_3_sigma=yes top10_recall=10/10 counts_in_range=10/10`; `sketch bench` exits with 3 if
  the worst HyperLogLog RMSE exceeds 1.25x theory, any item exceeds `epsilon * N` more often than
  `delta`, or any estimate is below its true count; the OSV audit fails on any known
  vulnerability. Each step prints its result as a `::notice` (or `::error`) annotation.
- **Mistake-proofing in the code:** constructors reject out-of-range precision, depth, width,
  epsilon, delta and k; negative counts and total overflow throw before any counter changes;
  `generate` refuses to overwrite a file; log lines, client fields and `--exact` are bounded.
- **Reproducible build:** pinned plugin versions, Enforcer for JDK and Maven versions, a fixed
  `project.build.outputTimestamp`, Actions pinned to commit SHAs.
